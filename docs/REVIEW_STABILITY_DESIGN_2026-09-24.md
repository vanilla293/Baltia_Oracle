# ПИФИЯ 5.3.0 — второй проход: исполнение, устойчивость и интерфейс

Дата: 24 сентября 2026 года. Исходник: `pythia_v5.3.0_a2b8a3a.zip`.
Итоговый архив: `pythia_v5.3.0_stability_design.zip`.

Эта сборка включает первый проход из `REVIEW_2026-09-24.md` и следующие изменения. Первый отчёт описывает состояние предыдущей сборки; актуальные результаты и ограничения приведены здесь. Номер приложения оставлен 5.3.0, новая сборка определяется именем архива.

## Что сохранено

Тексты промптов, состав моделей и стратегия принятия решений ИИ не переписывались. Изменения логики относятся к исполнению, восстановлению состояния, учёту сделок и обработке ошибок. Исходный ZIP и ранее выданный архив `reviewed` не изменены.

Файлы `backend/prompts.py`, `backend/prompts_council.py`, `backend/prompts_mission.py` побайтово совпадают с оригинальным ZIP. Дополнительно сравнение AST не обнаружило удалённых или изменённых строковых литералов длиннее 180 символов в `ai_pilot.py`, `mission.py`, `council.py`, `explain.py`, `ai.py`, `watch.py`.

## Исполнение и восстановление после сбоя

| Сценарий | Исправление |
|---|---|
| Брокер принял заявку, но HTTP-ответ потерялся | UUID запроса сохраняется до отправки. Неизвестный результат остаётся в сохранённом состоянии; восстановление проверяет прежнюю заявку и не создаёт новую вслепую. Ошибка записи на диск блокирует отправку. |
| Частичное исполнение входа или выхода | Учёт идёт по приросту исполненного количества. Повторный ответ брокера не удваивает закрытые лоты и результат. Принятая заявка не считается полностью исполненной. |
| Не удалось отменить заявку | Ожидающая заявка остаётся в состоянии пилота. Повторные попытки ограничены по частоте, отменённое намерение не путается с подтверждённой отменой. |
| Замена защитного стопа прервалась на запросе | Сохраняются UUID и исходные параметры запроса. Пока исход неизвестен, конфликтующие новые стопы и закрытия блокируются. |
| Паника одновременно с завершением анализа или перезапуском | Отменённый совет не может позднее запустить пилот. Аварийное закрытие сохраняет запрос до отправки, переживает отмену HTTP-запроса клиента и не запускается второй раз параллельно. |
| Остановленная вручную миссия | Сохранённое намерение остановки учитывается при восстановлении; сторож не возобновляет торговлю самовольно. Незавершённые заявки продолжают учитываться при разрешении новой миссии. |
| Повреждённое или недоступное состояние аварийных заявок | Новые действия блокируются с понятной причиной. Ошибка чтения не считается отсутствием незавершённых заявок. API возвращает JSON с HTTP 503 и пояснением. |
| Запаздывающие данные портфеля | Согласование учитывает собственные заявки, чтобы не принять их исполнение за независимое ручное изменение позиции. |
| Некорректные цены и количество | Добавлены проверки конечных чисел и округления дробной цены Quotation с переносом nano. Идентификатор заявки брокера сохраняется отдельно от UUID клиента. |

Для проверки контракта заявки использовались официальные документы T-Invest: [OrdersService](https://developer.tbank.ru/invest/services/orders/methods), [GetOrderState](https://developer.tbank.ru/invest/api/orders-service-get-order-state), [StopOrdersService](https://developer.tbank.ru/invest/services/stop-orders/stoporders).

**Ограничение неопределённого стопа:** автоматическая повторная отправка с тем же UUID допускается только в пределах пяти минут. Это консервативное ограничение приложения, а не обещание брокера о сроке хранения ключа идемпотентности. Для более старого запроса или запроса без времени отправки автоматическое продолжение блокируется и требуется проверить заявку у брокера. Исправление не подменяет неизвестный исход догадкой об успехе или отказе.

## Журнал сделок и комиссии

- Одна брокерская операция может подтверждать несколько частичных закрытий, например 2 и 3 лота из одного исполнения на 5 лотов. Ранее первое сопоставление могло целиком занять операцию и оставить вторую сделку без подтверждения.
- Теперь сохраняются использованные диапазоны исполнений, их цены и уже распределённые комиссии. После повторной сверки и перезапуска те же объёмы не списываются повторно.
- Отдельные операции комиссий распределяются по реально использованному объёму; при росте частичного исполнения учитывается оставшаяся сумма комиссии.
- Неучтённый остаток операции может стать отдельной восстановленной сделкой один раз.
- В `store_v5` добавлено поле `ops_alloc` через существующую миграцию. Существующие записи и таблицы не удаляются. Старые подтверждённые записи без новой детализации сохраняют прежний способ резервирования операции целиком.

## Сохранение настроек и завершение работы

- Настройки сначала записываются атомарно на диск и только после успеха публикуются в памяти. При ошибке записи старое состояние сохраняется.
- Повреждённый JSON настроек больше не превращается молча в пустую конфигурацию. Ошибка видна, файл сохраняется для восстановления.
- NaN, Infinity и переполнение числовых настроек обрабатываются явно.
- При завершении сервера отслеживаются задачи совета, миссий, пилотов, сканеров, чата, пояснений и отложенной сверки. Их отмена и завершение происходят до закрытия HTTP-клиентов. Прямое аварийное закрытие имеет отдельную задачу, завершения которой сервер дожидается.
- Событие, пришедшее во время генерации пояснения, не теряется; устаревшая задача не записывает результат поверх новой миссии.

## Интерфейс

- Переработаны светлая и тёмная темы: спокойный фон, контрастная навигация, бирюзовый акцент, согласованные карточки, отступы, типографика и состояния фокуса.
- У четырёх разделов появились понятные заголовки и краткое описание назначения.
- На широком экране график и управление пилотом стоят рядом. Сводка позиции, уровни, результат и время до перепроверки читаются раньше второстепенных подробностей.
- Подготовка миссии сворачивается после завершения, история пилота раскрывается отдельно. Пользовательский выбор раскрытия сохраняется между обновлениями.
- На телефоне используются нижняя навигация и адаптивные формы. Кольца показателей больше не сжимаются с выходом за границу карточки.
- Сохранены рабочие сценарии: новости и совет, собственный взгляд, запуск и ведение миссии, график, журнал, дозор и чат.

## Оптимизация

`index.html` уменьшен с **552 168 до 29 690 байт** за счёт переноса встроенных стилей и логики в `frontend/static/terminal.css`, `terminal.js` и `workspace.css`. Это уменьшение HTML, а не общего объёма первой загрузки: вынесенные файлы также нужны браузеру. Статические файлы используют существующую проверку ETag; повторная загрузка может получить 304 без повторной передачи содержимого.

Одновременные полные обновления состояния объединяются в один запрос. Ответ статуса, пришедший позже более свежего ответа по той же миссии, не откатывает экран назад. Сохранены исправления первого прохода для поиска, графика, чата и запросов предыдущего инструмента.

## Проверки

Работа разделялась между исполнителями, затем общий результат проверял отдельный агент. Одновременно использовалось не более трёх вспомогательных агентов. Найденные проверяющим ошибки исправлены; он повторно проверил изменения. Финальный общий прогон и браузерную проверку выполнил основной агент.

- **165 Python-тестов — пройдены.** Включая потерянные ответы, частичные исполнения, повторные отмены, аварийное закрытие, сбои диска и восстановления, конфигурацию, миграции, фоновые задачи и API.
- **18 JavaScript-тестов — пройдены.** Включая синтаксический разбор всего поставляемого скрипта, управляемые задержки ответов, объединение запросов, защиту актуальной миссии, график, поиск и чат.
- Проверяющий дополнительно прогнал **1000 детерминированных комбинаций распределения объёмов** для журнала. Это дополнительная проверка, не отдельная постоянная тестовая команда в архиве.
- Встроенные самотесты `ai_pilot`, `trader_broker`, `store_v5`, `mission`, `explain`, `council`, `watch`, `ledger` — пройдены. В первом проходе также проверены самотесты `api_v5`, `api_council`, `api_mission`.
- `compileall` и `git diff --check` — без ошибок.
- В браузере проверены ширины 320, 390, 1440 и 1920 px, обе темы, запуск демо-миссии, график и его полноэкранный режим, сворачивание подготовки, формы и журнал. В проверенных сценариях горизонтального переполнения страницы и ошибок JavaScript не обнаружено.
- Готовое приложение повторно запущено после последних изменений в режиме моков. Запуск сервера завершился успешно.

Окружение: Windows, Python 3.12.14, pytest 9.1.1. Общий прогон содержит пять предупреждений зависимостей об устаревающем `on_event` и использовании httpx в TestClient; падений нет.

Проверки выполнялись с `PYTHIA_MOCK_AI=1`, `PYTHIA_MOCK_TINKOFF=1`, `PYTHIA_DRY=1`, отключённым Telegram. Реальные торговые заявки, платные вызовы ИИ и сообщения Telegram не отправлялись. Проверки подтверждают обработанные сценарии, но не исполнение у реального брокера, доступность внешних сервисов или доходность стратегии.

## Запуск и обновление

1. Распаковать новый архив в отдельный каталог. Запуск — прежними `start.bat` или `start.sh`; для первого знакомства подходит режим демо.
2. Перед обновлением существующей установки остановить её сервер и сохранить резервную копию `data`. Не запускать две установки одновременно на одном реальном счёте.
3. Если нужна прежняя история и настройки, перенести собственный каталог `data` в новую установку при остановленных серверах. Новое поле журнала добавится обычной миграцией. Исходная конфигурация чистого старта и сброса ключей не менялась.

Архив не содержит `data`, ключей, тестовых баз, `.venv`, `.git` и кешей. Также исключён вложенный `archive/pythia_4.5.4_zerotouch.zip`: внутри исторической сборки обнаружены собственная база и файл настроек. Оригинал этого вложенного архива на диске не изменён. Тесты и `requirements-dev.txt` включены. Для самостоятельной перепроверки:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pytest -q
node --test tests/test_frontend.cjs
```

Для последней команды нужен Node.js с поддержкой `node:test`. Сам терминал Node.js не требует.

## Оставшиеся ограничения

- Сетевой режим исходного проекта сохранён: стандартные скрипты слушают `0.0.0.0`, разрешён широкий CORS, единой авторизации управляющих API нет. Изоляция доступа и сопряжение устройств требуют отдельного изменения сетевого контракта; сервер не следует публиковать в открытый интернет.
- Стили и код вынесены из HTML, но `terminal.js` остаётся крупным файлом. Дальнейшее разделение на независимые модули имеет смысл делать по подсистемам с сохранением текущих регрессионных тестов.
- Сопоставление журнала опирается на доступные операции брокера, инструмент и временные окна. Сложные смешанные ручные операции и задержки выгрузки всё ещё требуют сверки с брокерским отчётом.
- Не проводились нагрузочные испытания на большом реальном архиве или длительный прогон с живым брокером. Гарантия отсутствия всех ошибок не заявляется.
